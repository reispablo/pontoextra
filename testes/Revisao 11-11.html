01 • Fundamentos

O que uma API REST organiza?

Uma API define um contrato para que sistemas troquem dados. Em REST, trabalhamos com recursos, identificados por rotas, e usamos métodos HTTP para expressar a ação desejada.

ClienteNavegador, aplicativo ou teste Cypress.
→
RequisiçãoMétodo + rota + headers + body.
→
RespostaStatus + headers + body.

Recurso

É a entidade manipulada pela API: cliente, produto, pedido ou configuração.

Coleção

/api/clientes representa o conjunto de clientes.

Item específico

/api/clientes/42 normalmente representa o cliente cujo ID é 42.

Boa rota REST: prefira substantivos que identifiquem recursos. O método já comunica a ação: GET /clientes/42, e não GET /buscarCliente/42.

02 • Métodos HTTP

Qual método usar?

Observe três perguntas: o que acontecerá com o recurso, qual rota será chamada e que resultado deve ser confirmado.

GET

Consultar

GET /api/clientes/42

Busca dados sem criar, alterar ou excluir o recurso.

200 OK404 Not Found
POST

Criar

POST /api/clientes

Envia dados para criar um novo item na coleção.

PUT

Substituir/atualizar

PUT /api/clientes/42

No contrato estudado, envia o conjunto completo de campos editáveis.

Excluir

DELETE /api/clientes/42

Remove o item identificado na rota.

204 No Content404 Not Found
Atenção ao PUT: a regra exata depende do contrato da API. Nesta revisão, considere PUT como atualização completa do recurso. Para atualização parcial, muitas APIs utilizam PATCH.

03 • Anatomia

Request e response

O teste não deve olhar apenas o status. Método, rota, autenticação, body, contrato da resposta e estado final formam a evidência completa.

Exemplo de requisição

POST /api/clientes HTTP/1.1
Content-Type: application/json
Authorization: Bearer ACCESS_TOKEN

{
  "nome": "Cliente Teste",
  "email": "cliente.teste@exemplo.com"
}

Exemplo de resposta

HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/clientes/42

{
  "id": 42,
  "nome": "Cliente Teste",
  "email": "cliente.teste@exemplo.com"
}
ParteFunçãoExemplo
MétodoIndica a intenção da chamada.POST
RotaIdentifica o recurso ou coleção./api/clientes
HeadersTransportam metadados, tipo do conteúdo e autenticação.Content-Type e Authorization
BodyContém os dados enviados ou recebidos.Objeto JSON
StatusResume o resultado HTTP.201 Created
Segurança: nunca publique senha, token real, cookie de sessão ou dados pessoais nas evidências. Em exemplos, use valores fictícios como ACCESS_TOKEN.

04 • Códigos HTTP

O status conta parte da história

A família indica a categoria geral: 2xx significa sucesso, 4xx aponta um problema relacionado à requisição e 5xx indica falha interna do servidor.

200 OK

A operação foi concluída com sucesso e existe uma representação no corpo. É comum em consultas e atualizações.

×
201 Created

Um novo recurso foi criado. É a resposta mais específica para um POST de cadastro bem-sucedido.

Não confunda: receber 200 não prova sozinho que a funcionalidade inteira está correta. Depois de um PUT, por exemplo, um novo GET pode ser necessário para confirmar a persistência.

05 • Estado final

Como validar um fluxo CRUD

Uma sequência de chamadas ajuda a confirmar não só a resposta imediata, mas também a mudança real do estado do recurso.

POST

Crie o cliente e guarde o ID retornado.

GET

Consulte o ID e confirme os dados criados.

PUT

Atualize o recurso com novos dados.

GET

Confirme que a alteração foi persistida.

DELETE

Exclua exatamente o recurso criado no teste.

GET

Espere 404: o recurso não deve mais existir.

Evidência forte: valide o status, o formato do body, os valores importantes e uma consulta posterior. Se a API retornar 201, mas o recurso não puder ser consultado, o cenário deve falhar.

06 • Automação

Interpretando um teste Cypress

cy.request() chama a API diretamente. Depois, o callback de .then() recebe a resposta para que as asserções verifiquem o comportamento esperado.

Consulta autenticada

it('lista os clientes', () => {
  cy.request({
    method: 'GET',
    url: '/api/clientes',
    headers: {
      Authorization: `Bearer ${token}`,
    },
  }).then((resposta) => {
    expect(resposta.status).to.eq(200)
    expect(resposta.body.data).to.be.an('array')
    expect(resposta.body.count)
      .to.eq(resposta.body.data.length)
  })
})
method + url
Fazem um GET na coleção de clientes.
Authorization
Envia o token no padrão Bearer.
status 200
Confirma o sucesso HTTP da consulta.
data array
Valida parte do contrato do body.
count
Compara a contagem informada com o tamanho real da lista.

Cenário negativo: validação de e-mail

cy.request({
  method: 'POST',
  url: '/api/clientes',
  headers: { Authorization: `Bearer ${token}` },
  body: { nome: 'Cliente Teste', email: 'email-invalido' },
  failOnStatusCode: false,
}).then((resposta) => {
  expect(resposta.status).to.eq(422)
  expect(resposta.body.error.code).to.eq('validation_error')
  expect(resposta.body.error.fields.email).to.exist
})
Por que usar failOnStatusCode: false?
Para impedir que o Cypress encerre o comando automaticamente ao receber um status 4xx ou 5xx. Assim, o teste consegue analisar a resposta de erro esperada.
O que essa opção não faz?
Ela não transforma erro em sucesso e não aprova o cenário. As asserções ainda precisam confirmar o status e o contrato corretos.
Como ler qualquer teste de API?
  1. Identifique o cenário descrito no it.
  2. Localize método, rota, headers e body.
  3. Descubra qual resposta é esperada.
  4. Traduza cada expect em uma regra verificável.
  5. Conclua o que o conjunto das asserções comprova — e o que ainda não comprova.
Qual a diferença entre status e contrato?

O status resume o resultado HTTP. O contrato descreve a estrutura e os tipos do body. Um endpoint pode devolver 200 e ainda assim estar incorreto se data deveria ser um array, mas veio como texto.

07 • Autoavaliação

Teste sua revisão

Responda sem consultar as seções anteriores. A correção acontece somente no seu navegador e nenhum dado é enviado.

1. Qual chamada consulta um cliente específico sem alterar dados?

Resposta: GET consulta o recurso indicado na rota.

2. Qual status comunica especificamente que um cadastro criou um recurso?

Resposta: 201 Created indica que um novo recurso foi criado.

3. O que informa o header Content-Type: application/json?

Resposta: Content-Type descreve o tipo do conteúdo transportado no body.

4. Uma rota protegida foi chamada sem token. Qual status é esperado?

Resposta: 401 Unauthorized indica autenticação ausente ou inválida.

5. Qual chamada representa uma atualização completa do cliente 42 no contrato estudado?

Resposta: PUT atualiza o item identificado; neste contrato, envia os campos editáveis completos.

6. Após um DELETE bem-sucedido e sem body, qual status é comum?

Resposta: 204 indica sucesso sem conteúdo no corpo da resposta.

7. Por que usar failOnStatusCode: false em um teste negativo?

Resposta: a opção permite analisar a resposta de erro; ela não substitui as asserções.

8. Um PUT devolveu 200, mas o GET seguinte mostrou os dados antigos. Qual conclusão é correta?

Resposta: é necessário validar o estado final. Status de sucesso não compensa dados não persistidos.

9. O JSON está bem formado, mas o e-mail viola a validação. Qual status é adequado?

Resposta: 422 é usado quando o conteúdo é compreendido, mas falha nas regras de validação.

10. Qual conjunto produz a melhor evidência de um cadastro?

Resposta: a combinação verifica resposta, contrato e persistência do novo recurso.
